# Data Generator 회고 — 값을 만드는 것에서 계약과 상태를 설계하는 것으로

> 기준: 2026-09-14, 로컬 `b4f1b88` 조사. 상세 사건은 [DEVELOPMENT_HISTORY.md](DEVELOPMENT_HISTORY.md), 근거 위치는 [EVIDENCE.md](EVIDENCE.md)에 있다. 아래 1인칭 문장은 채용 자료용 초안이며, 본인이 실제로 이해·검토·판단한 범위로 수정해야 한다.

## 1. 경험의 중심 문장

**센서 시뮬레이터도 여러 서비스가 동일하게 해석할 수 있는 데이터 계약과 상태 일관성이 필요했다.**

처음 목적은 실제 센서가 충분하지 않은 상황에서도 팀이 개발을 진행할 수 있도록 값을 공급하는 것이었다. 이후에는 단순히 임의의 숫자가 나오는지보다 다음 질문이 중요해졌다.

- 같은 재배의 센서는 같은 환경 변화를 관찰하는가?
- 같은 장치의 섭씨와 화씨가 서로 환산 가능한가?
- 센서가 많아졌다는 이유로 환경이나 제어 효과가 여러 번 진행되지 않는가?
- 채널을 지운 뒤 다른 장치의 공유 상태까지 초기화되지는 않는가?
- 같은 제어 요청이 다시 도착하면 상태를 또 바꾸는가?
- 잘못된 초기 정보나 변경 이벤트를 받은 경우 어떤 상태를 보존해야 하는가?

이 질문들이 공용 환경, 관측값, 단위, cycleId, 작업 예약, 명령 이력을 각각 구분하는 설계로 연결됐다. 이는 농장 물리 모델의 정확도를 높였다는 성과가 아니라 **개발용 데이터와 서비스 동작의 일관성을 보강한 경험**이다.

## 2. 주요 설계 판단과 대가

### 2.1 공용 환경과 센서 관측값을 분리한 이유

**이전 구조의 제약:** 채널별 독립 Random Walk에서는 같은 재배의 온도 센서가 서로 무관한 방향으로 움직이고, 같은 장치의 다른 단위 채널을 연결하기 어렵다.

**선택한 구조:** 환경 상태는 `(cultivationId, sensorType, canonicalUnit)`, 관측 상태는 여기에 `deviceEui`를 더한 키로 관리한다. 공용 환경값에 장치의 고정 bias와 시간에 따른 deviation을 반영한 후 등록 단위로 변환한다.

**얻은 점:** 공통 환경 변화와 장치별 관측 차이를 함께 표현한다. 같은 EUI의 섭씨·화씨는 별개의 전송 채널이지만 같은 관측값을 사용한다.

**대가·한계:** 공유 상태 수명 관리와 키 관계가 복잡해진다. bias·deviation은 실측 센서로 보정한 모델이 아니다. “현실 재현 정확도 향상”이라는 수치는 없다.

근거: [SharedEnvironmentSensorValueGenerator](../../../src/main/java/site/yesaido/data_generator/generator/SharedEnvironmentSensorValueGenerator.java), [SensorObservationProjector](../../../src/main/java/site/yesaido/data_generator/generator/SensorObservationProjector.java), 사건 D07.

### 2.2 cycleId와 중복 작업 예약이 둘 다 필요한 이유

두 장치는 서로 다른 문제를 해결한다.

| 장치 | 해결하는 문제 | 범위 |
|---|---|---|
| cycleId | 같은 주기의 여러 채널 호출이 공용 환경·제어 효과를 반복 적용하는 문제 | 환경/관측 키별 계산 |
| 재배 ID 실행 예약 | 이전 주기의 생성 작업이 남았는데 다음 작업이 겹치는 문제 | 재배별 작업 제출·실행 |

스케줄러가 발급한 cycleId를 제출 시점의 불변 센서 목록과 함께 작업에 캡처한다. 실행 시점에 새 cycle을 만들지 않는다. 같은 cycle은 상태를 재사용하고 이전 cycle은 거부한다. 작업 예약은 정상 종료뿐 아니라 제출 거절·예외에서도 해제한다.

**얻은 점:** 센서 개수와 상태 진행 횟수를 분리하고, 실패 후 예약이 영구히 남는 경로를 피한다.

**대가·한계:** 앞선 작업이 남으면 다음 주기를 건너뛴다. 샘플 무손실 정책이 아니며, MQTT 전송이 모두 끝날 때까지 예약을 붙잡는 것도 아니다. 둘 다 프로세스 내부 제어로 다중 replica의 분산 락을 대체하지 않는다.

근거: [EnvironmentRandomWalkGenerator](../../../src/main/java/site/yesaido/data_generator/generator/EnvironmentRandomWalkGenerator.java), [CultivationTaskCoordinator](../../../src/main/java/site/yesaido/data_generator/service/CultivationTaskCoordinator.java), 사건 D08·D09.

### 2.3 빠른 초기화를 위해 검증을 생략하지 않은 이유

센서 등록 정보와 임계값이 없는 상태에서 값을 발행하면 실제 등록 내용과 다른 데이터가 흘러갈 수 있다. 따라서 snapshot 응답 전체를 먼저 변환·검증한 후 캐시를 채우고, 그다음 변경 이벤트 listener를 시작한다. scheduler 역시 초기화 상태를 확인한다.

**얻은 점:** 잘못된 snapshot을 부분 반영하는 것을 피하고, 빈 상태와 오류 상태를 구분한다.

**대가·한계:** 초기화 서비스에 장애가 있으면 시작이 늦어지거나 최종 실패한다. snapshot과 이벤트의 완전한 원자적 전환을 보장하는 프로토콜은 아니다. 이벤트 revision이 없어 전체 순서 보장에는 남은 과제가 있다.

근거: [CultivationSensorSynchronizationService](../../../src/main/java/site/yesaido/data_generator/service/CultivationSensorSynchronizationService.java), 사건 D04.

### 2.4 가상 제어 API도 명령 계약이 필요한 이유

단순한 ON/OFF 값만 받으면 같은 요청의 재시도인지 새로운 명령인지 알기 어렵다. 현재는 commandId, 요청 내용, 시각, 만료, 현재 반대 장치 상태를 구분한다.

**선택한 순서:** 초기화 확인 → 기존 commandId 확인 → 만료 → stale → 반대 장치 충돌 → 상태 적용.

같은 명령이면 이전 응답을 돌려주고, 같은 ID를 다른 내용에 사용하면 거부한다. 적용·거절·재처리는 로그에서도 구분된다.

**얻은 점:** “요청을 받았다”와 “새로 적용했다”를 구별할 수 있다.

**대가·한계:** 명령 이력은 인메모리이며 재시작 후 영구 멱등성을 보장하지 않는다. `synchronized`의 범위도 한 인스턴스다. 실제 장치 안전성을 인증하거나 물리 제어를 검증한 결과가 아니다.

근거: [VirtualActuatorService](../../../src/main/java/site/yesaido/data_generator/service/VirtualActuatorService.java), 사건 D11.

## 3. 시행착오에서 배운 것

### 3.1 목록의 개수를 업무 의미로 해석한 설계

이전 코드에는 임계값 목록 1개를 수정, 4개 이상을 전체 교체로 보고 2~3개는 오류 처리하는 분기가 있었다. 2026-08-16 `e712209`에서는 이를 제거하고, 빈 목록은 종료·정리, 1개 이상은 모두 upsert하는 방식으로 바꿨다.

**회고:** 구조가 우연히 맞는 샘플만으로 계약을 정의하면 데이터 조합이 바뀔 때 깨진다. 데이터 크기와 도메인 의도는 다른 정보다. 다음에는 변경 종류·전체 교체 여부·삭제 의미를 명세와 테스트에서 함께 확정하고 싶다.

확인된 것은 코드 변경과 테스트다. 이 문제로 실제 장애가 몇 번 발생했는지, 팀원이 어떻게 발견했는지, 해결에 얼마나 걸렸는지는 기록이 없어 미확인으로 남긴다.

### 3.2 눈에 비슷한 단위가 코드에서는 다른 값이었다

습도 `%RH → %`, 섭씨 `°C → ℃ → °C` 변경 이력이 있다. 최종 로컬 코드의 계약은 `°C`, `°F`, `%`, `ppm`, `lux`다. 현재 변환기는 다른 문자를 무조건 같은 단위로 취급하지 않는다.

**회고:** unit은 화면 장식이 아니라 채널 식별과 변환 가능 여부를 결정하는 계약이다. 코드 한 곳의 상수만 바꾸기보다 발행자·소비자·fixture·테스트·문서를 함께 맞춰야 한다.

이 사건과 Ai 서버의 `unit` 쿼리 파라미터 누락 문제는 서로 다른 변경이다. 둘을 합쳐 하나의 원인·개선 성과로 적지 않는다.

### 3.3 공유 상태는 생성보다 삭제가 더 까다로웠다

섭씨·화씨가 같은 관측 상태를 공유하면 화씨 채널만 지웠다고 관측값을 초기화하면 안 된다. 다른 EUI가 같은 공용 환경을 사용 중인 경우도 마찬가지다. 현재는 캐시의 채널을 먼저 제거한 뒤 남은 참조를 확인해 관측 상태와 환경 상태를 단계적으로 정리한다.

**회고:** 객체를 어떤 키로 공유할지 정했다면 언제 해제할지도 함께 설계해야 한다. 데이터가 생성되는 정상 흐름뿐 아니라 삭제·재등록·동시 실행을 검증 대상으로 포함해야 한다.

근거: [SharedGenerationStateLifecycle](../../../src/main/java/site/yesaido/data_generator/service/SharedGenerationStateLifecycle.java), 사건 D12.

### 3.4 문서도 구현과 함께 바뀌어야 했다

9월 14일 경험 문서화에서 루트 README의 독립 Random Walk 설명과 현 공용 환경 코드가 다름을 확인했다. 이는 그날 새로 발견한 문서 불일치다. 과거에 이미 해결한 장애나 리팩터링 성과로 바꾸어 적지 않는다.

**회고:** 구현을 바꿀 때 코드·테스트뿐 아니라 설명의 핵심 개념과 운영 제약도 함께 확인하는 체크리스트가 필요하다.

## 4. 검증에서 말할 수 있는 것과 없는 것

| 말할 수 있는 것 | 증거가 더 필요한 것 |
|---|---|
| 동일 cycle 상태 재사용과 오래된 cycle 거부 테스트 | 모든 부하 조건에서 정확히 1초 이내 전송 |
| 작업 실패·거절 후 예약 해제 테스트 | 처리량·개발 기간 개선율 |
| 단위 변환·미지원 조합 검증 | 실제 센서 측정 정확도 |
| 명령 replay·만료·stale·충돌 테스트 | 실제 농장 장치 안전성·장기 안정성 |
| 기존 Surefire 파일의 suite별 결과 | 현재 SHA의 최신 전체 테스트 통과 수 |
| 등록 정보 snapshot 복구 | 재시작 후 과거 환경값·명령 이력의 완전 복구 |

이번 문서화에서는 테스트나 운영 점검을 새로 실행하지 않았다. 과거 보고서의 숫자를 합쳐 성과를 부풀리지 않는다. 테스트 통과는 지정한 계약의 근거이고 실제 농업 환경 성능의 근거는 아니다.

## 5. 다음에 보완하고 싶은 것

아래는 **후속 제안**이지 완료한 구현이 아니다.

1. **계약 변경 기록:** 센서 단위·이벤트 의미의 변경 사유, 영향 서비스, 전환 순서를 짧은 ADR로 남긴다.
2. **재현 가능한 시나리오:** 현재 Random Walk와 별도로 seed·입력·명령 타임라인을 고정하는 검증 경로를 검토한다. 지금 모든 실행을 동일하게 재생할 수 있다고 말하지 않는다.
3. **이벤트 순서:** revision 또는 동등한 버전 정책으로 snapshot 이후의 변경 순서를 어떻게 판단할지 팀과 결정한다.
4. **장기 상태 수명:** 명령 이력의 TTL·최대 보관량·정리 시점을 검토한다. 코드상 한계이며 OOM 발생을 확인한 것은 아니다.
5. **readiness:** snapshot 준비, listener 준비, MQTT 연결을 서비스 준비 상태에 어떻게 반영할지 정한다.
6. **다중 인스턴스:** 재배 분할 소유권·외부 상태 저장·분산 예약 중 필요 조건을 먼저 정한다. 무조건 replica 수만 늘리지 않는다.
7. **계측:** 스킵된 주기, 작업 대기·실행 시간, MQTT 실패, 상태 수를 수집해 과부하와 연결 문제를 분리한다.
8. **실측 비교:** 실제 센서 표본을 확보했을 때만 오차와 환경 변화 형태를 비교한다. 그전에는 가상 환경의 물리적 정확성을 주장하지 않는다.

## 6. 포트폴리오와 자기소개서 활용

### 6.1 이력서 문장 후보

> Java/Spring 기반 가상 센서·액추에이터 서비스를 개발하고, 공용 환경과 장치 관측값 분리, 단위 변환, MQTT 발행 및 재배 단위 실행 제어를 구현했습니다.

### 6.2 포트폴리오 한 페이지 구성

- **제목:** 센서 수가 늘어도 같은 환경을 관측하도록 설계했습니다.
- **문제:** 독립 채널 난수는 공통 환경과 단위 환산의 일관성을 표현하기 어려웠습니다.
- **판단:** 공용 환경·장치 관측·전송 채널의 키를 분리했습니다.
- **구현:** 환경 → bias/deviation → 등록 단위 변환, cycleId 재사용.
- **검증:** 동일 주기·동시 호출·채널 삭제·변환 경계 테스트.
- **한계:** 실측 보정 전의 개발용 시뮬레이터이며 분산 실행 보장은 별도 과제입니다.

실제 그래프나 API 응답을 추가할 때는 캡처 환경·날짜·모델이 가상임을 표시한다. 정량 비교 원자료가 없다면 개선율을 쓰지 않는다.

### 6.3 자소서 초안 — 상태 일관성 사례

> 저는 동작하는 기능을 만드는 데서 그치지 않고, 여러 데이터가 같은 의미를 유지하는지 확인하려고 했습니다. 가상 센서 서비스에서 같은 재배의 채널을 독립적으로 생성하면 공통 환경 변화와 단위 환산 관계를 표현하기 어렵다는 제약이 있었습니다. 공용 환경과 장치 관측값을 분리하고, 같은 생성 주기의 호출에는 상태를 재사용하도록 cycleId를 전달했습니다. 단위 변환·동시 호출·삭제 후 남은 참조·작업 거절 이후 예약 해제 사례를 테스트로 정리했습니다. 이 과정에서 상태를 생성하는 방법뿐 아니라 공유·변경·삭제 경계를 함께 설계해야 함을 배웠습니다.

### 6.4 자소서 초안 — 계약 수정 사례

> 센서 임계값 이벤트를 연결하면서 목록 크기로 등록과 수정 의미를 추정하는 코드를 확인했습니다. 이 방식은 2~3개의 항목을 정상 처리하지 못하는 제약이 있었습니다. 빈 목록은 상태 정리, 1개 이상은 모든 항목 upsert라는 계약으로 처리 흐름을 명확하게 바꾸고 관련 경계 테스트를 정리했습니다. 이를 통해 샘플 데이터가 우연히 맞는 것과 다양한 요청에서 계약이 유지되는 것은 다르다는 점을 배웠습니다.

**제출 전 보강할 기억:** 누가 최초 현상을 발견했는가, 나는 어떤 대안을 비교했는가, 팀과 어떻게 합의했는가, 어떤 테스트를 직접 확인했는가. 코드에 없는 대화·갈등·리더십·시간 절약 수치는 만들어 넣지 않는다. AI 도구를 이용했다면 직접 이해·검토·검증한 역할을 중심으로 말한다.

## 7. 면접 질문과 답변의 기준

### Q1. 왜 Data Generator가 필요했나요?

실제 센서와 재배 환경이 충분하지 않은 개발 환경에서 팀의 수집·판단·제어 연동을 진행할 데이터가 필요했습니다. 실제 측정처럼 보이는 숫자를 전시하는 것이 아니라 팀의 MQTT 계약으로 데이터를 공급하고 가상 제어 효과를 확인할 수 있도록 만들었습니다. 실제 농장 검증과는 구분합니다.

### Q2. 왜 독립 난수 대신 Random Walk를 사용했나요?

현재값에 제한된 변화량을 더해 이전 값과 연결된 변화를 만들기 위해서입니다. 현 구조에서는 이것을 재배별 공용 환경에 적용하고, 장치별 관측 차이를 별도로 둡니다. 실제 환경의 시간 특성을 학습한 확률 모델이라는 뜻은 아닙니다.

### Q3. 같은 재배의 온도 센서는 전부 같은 값인가요?

공용 환경은 같지만 EUI별 고정 편향과 변화하는 편차가 있으므로 서로 다를 수 있습니다. 반면 같은 EUI의 섭씨·화씨는 동일한 관측값을 단위 변환한 것입니다.

### Q4. cycleId가 없으면 무엇이 잘못되나요?

센서별 호출마다 공용 환경을 갱신하면 센서가 많은 재배에서 한 주기에 제어 효과가 여러 번 적용될 수 있습니다. cycleId로 환경 갱신 시점을 채널 호출 횟수와 분리했습니다.

### Q5. ConcurrentHashMap을 썼으니 모든 동시성 문제가 해결됐나요?

아닙니다. 키별 갱신에는 `compute`를 사용하고, 같은 재배 작업의 중복 제출에는 별도 예약을 사용합니다. 여러 상태 저장소 전체의 원자성이나 다른 프로세스의 작업까지 자동 보장하지 않습니다.

### Q6. 작업이 1초를 넘으면 어떻게 되나요?

같은 재배의 기존 작업이 대기 또는 실행 중이면 다음 제출을 건너뜁니다. 유한 큐에서 작업이 거절돼도 예약을 해제해 이후 주기를 받을 수 있게 합니다. 모든 샘플을 반드시 보존하는 설계는 아닙니다.

### Q7. MQTT 발행 성공이면 알림까지 성공한 것인가요?

아닙니다. 발행자 측 결과와 Rule Engine 처리·DB 저장·Notification 전달은 다른 단계입니다. 기본 QoS 0이므로 무손실도 주장할 수 없습니다. 종단 간 검증에는 각 단계의 로그·저장·수신 증거가 필요합니다.

### Q8. 같은 commandId가 다시 들어오면 어떻게 하나요?

같은 대상·요청 내용의 명령이면 기존 응답을 재사용하고 상태를 다시 적용하지 않습니다. 같은 ID를 다른 요청에 재사용하면 거부합니다. 이력은 인메모리이므로 재시작 후 영구 멱등성을 보장하지는 않습니다.

### Q9. 왜 기존 명령 확인이 만료 확인보다 먼저인가요?

이미 처리된 동일 요청의 재시도라면 새 상태 적용 없이 원래의 응답을 반환하기 위해서입니다. 처음 받는 요청일 때 만료·stale·충돌을 검사합니다. 적용 여부와 재응답을 구분한 계약입니다.

### Q10. snapshot을 받으면 이벤트 순서 문제까지 해결되나요?

아닙니다. 초기 기준 상태를 확보하고 준비되지 않은 발행을 막는 장치입니다. snapshot과 이벤트의 경계, 역순 이벤트에는 version/revision 등 별도 정책이 필요합니다.

### Q11. 가장 구체적으로 설명할 수 있는 시행착오는 무엇인가요?

임계값 목록을 1개와 4개 이상으로 나눠 업무 의미를 추정하던 코드를 바꾼 사례입니다. 실제 diff에서 2~3개를 거부하던 조건이 없어졌고, 빈 목록 정리와 1개 이상 upsert로 명확해졌습니다. 실제 장애 횟수나 해결 시간은 근거가 없어 말하지 않겠습니다.

### Q12. 이 서비스가 AI 모델 학습 데이터 생성기인가요?

확인한 범위에서는 팀의 센서 수집·제어 통합 개발에 사용하는 시뮬레이터입니다. Vision 학습은 별도의 이미지·라벨 데이터에 기반합니다. 이 가상 센서값으로 Vision을 학습했다거나 실제 재배 결과를 예측하도록 학습했다고 연결하지 않습니다.

### Q13. 본인이 만든 범위는 어디까지인가요?

저는 Data Generator의 생성·채널·단위·MQTT·snapshot·이벤트 반영·가상 제어와 관련 리팩터링·테스트를 담당했습니다. Cultivation의 원천 데이터 제공, Rule Engine 판단, Notification 전송, 인프라는 팀과 연결한 영역이며 해당 서비스 전체를 제 개인 구현으로 설명하지 않습니다.
