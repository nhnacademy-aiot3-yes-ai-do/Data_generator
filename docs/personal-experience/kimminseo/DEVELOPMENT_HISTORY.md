# Data Generator — 가상 센서를 팀의 통합 검증 환경으로 연결한 경험

> 작성 기준: 2026-09-14, 로컬 `Data_generator` HEAD `b4f1b88` 읽기 전용 조사. 원본 코드 수정, 테스트 재실행, 운영 접속은 하지 않았다. 이 문서는 확인 가능한 사건과 설계 판단의 기록이며, 기억나지 않는 회의·장애·소요시간까지 복원한 기록은 아니다. 세부 근거는 [EVIDENCE.md](EVIDENCE.md)를 참고한다.

## 1. 한눈에 보는 역할과 범위

**핵심 요약:** 실제 센서가 충분하지 않은 개발 환경에서, 등록된 센서 채널에 맞는 가상 값을 MQTT로 발행하고 가상 제어 요청의 효과를 다음 측정값에 반영하는 Spring Boot 서비스를 개발했다.

| 구분 | 기록할 내용 | 확인 상태 |
|---|---|---|
| 제작 배경 | 강의실에서 실제 재배 조건과 충분한 센서·장치를 갖추기 어려워 가상 데이터 공급이 필요했다. | 사용자 설명 + README의 실제 센서 없는 개발 환경 목적 |
| 개인 담당 | Data Generator의 센서 생성·MQTT·스케줄링·snapshot·변경 이벤트·가상 제어 및 리팩터링 작업 | 사용자 설명 + `kim75503` 계열 author의 관련 변경 이력 |
| 팀 연동 | Cultivation이 센서·임계값 정보를 제공하고 Rule Engine이 MQTT 데이터를 받아 판단·제어 요청을 보낸다. | 현재 클라이언트·이벤트·API 계약 |
| 개인 범위 밖 | Rule Engine의 임계값 판단 전체, 센서 DB 적재 전체, 실제 하드웨어 제어, Notification의 사용자 알림 전송, 인프라 전체 | 서비스 경계 명시 |
| 사용 기술 | Java 21, Spring Boot, OpenFeign, RabbitMQ, Eclipse Paho MQTT, 인메모리 상태, JUnit/Mockito | README·소스·테스트 코드 |

이력서에서 “버섯 재배 환경 전체를 구현했다”, “실제 농장의 자동 제어를 검증했다”로 확대하지 않는다. 시뮬레이터는 농장 환경의 물리·생물학적 정확성을 입증한 모델이 아니다. “모든 버섯은 어둡고 고온다습한 조건이 필요하다”는 식의 일반화도 제작 이유로 사용하지 않는다.

## 2. 서비스가 하는 일

### 시작 시점

```text
Cultivation의 센서·임계값 snapshot 조회
    → 응답 전체 검증·변환
    → 센서/임계값 캐시 초기화
    → RabbitMQ 변경 이벤트 listener 시작
    → 센서 생성 허용
```

초기 정보가 없는데 값을 먼저 발행하지 않도록 두 캐시의 초기화 완료 여부를 확인한다. snapshot 조회 실패에는 제한된 재시도와 backoff를 적용한다. 최종 실패하면 애플리케이션 시작이 실패한다. 빈 목록은 정상적인 빈 상태이고, null·중복 채널·잘못된 범위는 오류로 구분한다.

### 생성·제어 시점

```text
1초 스케줄 → 센서 snapshot → 재배별 작업 예약
    → 공용 환경값 갱신(환경 key + cycleId)
    → 장치별 관측 편향·편차 반영
    → 등록된 단위로 변환 → MQTT 비동기 발행
                                      ↓
                               Rule Engine [팀 영역]
                                      ↓ 내부 HTTP 제어 요청
                 가상 액추에이터 명령 검증·상태 적용
                                      ↓
                         다음 환경값에 방향성 효과 반영
```

1초는 **스케줄 주기**다. 작업 포화·중복 예약·네트워크 문제를 포함해 모든 채널의 종단 간 전송이 매초 반드시 완료된다는 보장은 아니다. MQTT 발행 성공도 Rule Engine의 처리, DB 저장, 사용자 알림 수신 성공과 동일하지 않다.

## 3. 설계를 이해하는 핵심 키

| 키 | 의미 | 중요한 이유 |
|---|---|---|
| `(deviceEui, sensorType, unit)` | 등록·삭제 및 전송 대상 채널 | 같은 장치의 섭씨와 화씨 채널을 구분한다. |
| `(cultivationId, sensorType, canonicalUnit)` | 재배의 공용 환경 상태 | 동일 재배에서 같은 물리량을 측정하는 장치가 환경 변화 방향을 공유한다. |
| `(environmentStateKey, deviceEui)` | 장치별 관측 상태 | 환경은 같아도 장치의 고정 편향과 시간에 따른 관측 편차는 다르게 만든다. |
| `(cultivationId, sensorType, unit)` | 등록 임계값 | 동적 센서 생성 계획을 정확한 타입·단위로 조회한다. |
| `cycleId` | 한 스케줄 호출의 생성 주기 | 여러 채널이 같은 환경을 조회해도 환경과 제어 효과를 여러 번 전진시키지 않는다. |

같은 EUI의 섭씨와 화씨는 서로 다른 전송 채널이지만, 같은 주기의 공용 환경·장치 관측값을 단위 변환해서 사용한다. 따라서 저장소 루트 README의 “단위가 다르면 각각 독립적인 Random Walk 상태”라는 과거 설명은 현 구현 설명으로 사용하지 않는다.

## 5. 사건·판단 노트

### D01. 실제 센서가 없어 개발을 진행하기 어려웠다

- **문제/제약:** 사용자 설명상 강의실에서 실제 재배 환경과 장비를 충분히 갖추기 어려웠다. 센서값이 없으면 하위 서비스의 수집·그래프·판단·알림 흐름을 연결하기 어렵다.
- **근거:** README의 개발 환경용 가상 센서 목적과 7월 28일 생성 로직 추가 이력.
- **선택:** 실제 데이터와 같은 팀 MQTT 계약으로 가상 데이터를 공급하는 별도 서비스 구성.
- **조치:** 센서 타입별 초기값·변화량·범위 설정과 Random Walk, 메시지 모델을 구현하고 발행 흐름에 연결했다.
- **결과:** 현재 코드에 가상 데이터 생성과 실제 메시지 경로 연동 구조가 존재한다.
- **한계:** 개발 기간 단축량, 실제 농장 재현 정확도는 측정 근거가 없다. 정해진 시나리오를 항상 동일하게 재생하는 시스템이라고도 단정하지 않는다.

### D02. 장치 한 개를 센서 한 종류로만 보면 채널이 충돌한다

- **문제/제약:** 같은 장치에 온도·습도 또는 섭씨·화씨가 함께 등록될 수 있다. 장치 ID만으로 식별하면 등록·삭제·단위 구분이 불명확하다.
- **근거:** 8월 12일 캐시의 타입·단위 채널 구조 변경 이력, `SensorChannelKey`, `SensorCache`.
- **선택:** 장치 메타데이터와 측정 채널을 분리했다.
- **조치:** `(deviceEui, sensorType, unit)` 채널 키 사용. upsert는 장치 정보를 갱신하고 채널을 합집합으로 병합하며 delete는 정확한 채널 하나만 제거한다. 다른 재배 소속으로 같은 EUI가 덮이는 요청은 거부한다.
- **결과:** 한 장치의 다른 측정 항목을 유지하면서 특정 채널만 변경할 수 있는 코드·테스트가 있다.
- **한계:** 이 구조만으로 서로 다른 서비스의 단위 표기 계약까지 자동 정규화되는 것은 아니다.

### D03. MQTT 데이터의 형식과 의미를 팀 계약에 맞췄다

- **문제/제약:** 생성하는 값이 숫자여도 토픽 구조·단위·시간 형식이 다르면 구독 서비스와 연결되지 않는다.
- **근거:** 8월 13일 MQTT 채널 계약 변경, `MqttTopicGenerator`, `MqttPayloadSerializer`, 관련 테스트.
- **선택:** 토픽에는 장치와 센서 타입을, payload에는 측정값과 등록 단위를 담았다.
- **조치:** 토픽 구성요소의 `/`, `+`, `#`, null 문자를 거부하고, 시간은 같은 순간을 `+09:00` 오프셋으로 직렬화했다. Paho 비동기 발행의 완료/실패를 `CompletionStage`로 전달한다.
- **결과:** 같은 온도 토픽에 섭씨·화씨가 발행되어도 payload의 `unit`으로 구분할 수 있다. 채널별 오류는 기록하고 다른 채널 생성은 계속한다.
- **한계:** 현재 기본 QoS 0 및 인메모리 메시지 영속성의 한계를 README에 명시했다. 데이터 무손실·Exactly Once는 보장하지 않는다.

### D04. 재시작하면 등록 정보가 사라지는 인메모리 캐시 문제

- **문제/제약:** 프로세스 메모리의 센서·임계값 정보는 재시작 뒤 남아 있지 않는다. 검증되지 않은 초기 데이터를 발행해서도 안 된다.
- **근거:** 8월 14일 snapshot 초기화 변경 및 현 `CultivationSensorSynchronizationService`, initializer, scheduler.
- **선택:** 시작 시 snapshot으로 기준 상태를 확보하고, 이후 변경 이벤트를 받는 흐름.
- **조치:** 전체 snapshot을 검증·변환한 후 캐시를 교체한다. 초기화 성공 후 listener를 시작하고, scheduler는 두 캐시의 완료 플래그를 확인한다. 재시도·backoff·최종 실패 처리가 있다.
- **결과:** 빈 snapshot과 잘못된 snapshot을 구분하고, 검증 실패 시 기존 캐시가 보존되는 테스트 사례가 있다.
- **한계:** snapshot과 이벤트의 원자적 전환·완전한 순서 보장을 뜻하지 않는다. 이벤트 revision이 없다는 제약이 남는다. 센서·임계값 복구와 이전 환경값·명령 이력 복구는 다르다.

### D05. 임계값 목록의 개수로 이벤트 의미를 추정했다가 수정했다

- **문제/제약:** 이전 코드는 목록 1개는 수정, 4개 이상은 전체 교체로 처리하고 2~3개를 오류로 취급했다. 데이터 개수로 업무 의도를 추정한 셈이다.
- **근거:** `e712209`의 실제 diff에서 개수 상수·검증 및 전체 교체 분기가 제거된다.
- **선택:** 크기 추론 대신 합의된 이벤트 의미를 명시적으로 따른다.
- **조치:** 빈 목록은 재배 생성 중지와 상태 정리, 1개 이상은 모든 항목 upsert로 변경했다. 현재 테스트에서는 과거에 거부되던 2개 항목의 upsert, 빈 목록 정리, 중복 키 거부를 확인한다.
- **결과:** 2~3개 항목을 잘못 거부하거나 다른 임계값을 목록 크기만 보고 지우던 분기를 제거했다.
- **한계:** 실제 장애 발생 횟수·운영 피해·팀 논의 원문은 확보하지 못했다. 빈 목록=종료라는 계약도 발행 서비스와 함께 유지해야 한다.

### D06. 새로운 숫자형 센서마다 전용 생성기를 추가해야 하는 제약

- **문제/제약:** 기본 4종 외 숫자형 센서를 등록했을 때 고정 생성기가 없으면 값 생성이 불가능하다.
- **근거:** 8월 13~14일 동적 생성 이력, `DynamicSensorConfigurationFactory`, `SensorGenerationPlanResolver`.
- **선택:** 등록된 임계값을 바탕으로 동적 생성 계획을 만든다.
- **조치:** 초기값은 임계값 중앙값, 생성 범위와 최대 변화량은 범위 폭 및 정책 비율로 계산한다. 지원하지 않는 고정 단위 또는 임계값 없는 동적 센서는 발행을 건너뛴다.
- **결과:** 전용 고정 생성기가 없는 숫자형 타입도 임계값 기반으로 생성할 수 있는 경로가 있다.
- **한계:** 사용자 정의 센서의 물리적 특성을 학습한 것이 아니다. 임의의 단위 변환이나 알 수 없는 장치 제어 효과를 만들어 적용하지 않는다.

### D07. 같은 재배의 센서인데 서로 무관하게 움직이는 값을 개선했다

- **문제/제약:** 채널별 독립 Random Walk는 같은 재배 환경을 관찰하는 장치 간의 공통 움직임과 같은 장치의 단위 환산 관계를 표현하기 어렵다.
- **근거:** 8월 27일 `c7abeaa`에서 기존 개별 생성기를 공용 환경·관측 투영 구조로 바꾼 diff와 현 코드.
- **선택:** “환경의 실제 상태”와 “센서가 관측한 값”을 개념적으로 분리했다.
- **조치:** 재배·타입·표준단위별 환경값에 EUI별 고정 bias와 연속적인 deviation을 더한다. 최종 관측값을 등록 단위로 변환한다.
- **결과:** 같은 환경 변화와 장치별 작은 차이를 동시에 표현하는 구조를 확보했다. 같은 EUI의 섭씨·화씨는 같은 관측값의 변환이다.
- **한계:** 실제 센서로 보정한 오차 모델이 아니다. 센서 정확도·현실성 개선율로 설명하지 않는다.

### D08. 센서 수가 많을수록 환경과 제어 효과가 여러 번 진행되는 것을 막았다

- **문제/제약:** 공유 상태를 여러 채널이 순서대로 조회하면서 매번 갱신하면 센서가 많은 재배의 환경이 한 주기에 여러 번 변한다.
- **근거:** `EnvironmentRandomWalkGenerator.calculateNextState`, `SensorObservationProjector.calculateNextState`, 동일 주기·동시 호출 테스트.
- **선택:** 시간 진행을 채널 호출 횟수가 아니라 `cycleId`로 결정했다.
- **조치:** 스케줄러에서 생성한 하나의 cycleId를 재배 작업과 모든 채널에 전달한다. 같은 키·같은 cycle은 기존 상태 반환, 오래된 cycle은 거부한다. `ConcurrentHashMap.compute`로 해당 키의 갱신 경계를 잡는다.
- **결과:** 동일 주기 재호출과 동시 호출이 환경값·제어 효과를 재적용하지 않는 테스트가 있다.
- **한계:** 프로세스 내부 보장이다. 여러 replica에 걸친 분산 중복 실행을 해결하는 락이 아니다.

### D09. 느린 작업이 다음 스케줄과 겹치는 것을 제한했다

- **문제/제약:** 주기마다 작업을 무조건 쌓으면 같은 재배의 작업이 겹치고 상태 순서가 흐트러질 수 있다.
- **근거:** `CultivationTaskCoordinator`, 고정 크기 executor, 중복·동시 제출·실패·거절 테스트.
- **선택:** 재배 단위로 실행 예약하고, 이전 작업이 대기·실행 중이면 다음 주기를 건너뛴다.
- **조치:** 불변 센서 목록과 cycleId를 제출 시 캡처한다. 완료·예외·executor 거절에서 예약을 해제한다. 작업 큐는 유한하며 거절 정책을 사용한다.
- **결과:** 한 재배의 중복 제출을 억제하고 실패 후 다음 주기를 다시 받을 수 있는 경로를 검증하도록 구성했다.
- **한계:** 건너뛴 샘플을 재생하지 않는다. 생성 작업 예약의 종료는 모든 MQTT 전송 완료를 기다리는 의미가 아니다. 처리량 개선 수치는 미측정이다.

### D10. 단위 문자열도 연동 계약이라는 것을 확인했다

- **문제/제약:** `%RH`와 `%`, `℃`와 `°C`는 비슷하게 보이지만 현 변환기에서는 서로 다른 문자열이다. 타입이 같아도 미지원 단위로 판단되면 발행을 건너뛸 수 있다.
- **근거:** 8월 18일 `335b225`의 `%RH → %`, 8월 31일 `2d5911c`의 `°C → ℃`, `b4f1b88`의 `℃ → °C` diff.
- **선택:** 팀과 사용하는 단위 표현을 맞추고 변환기·fixture·문서·테스트의 기대값을 동기화했다.
- **조치:** 최종 로컬 코드의 온도 표준단위는 `°C`, 습도는 `%`다. 화씨 환산은 수치 변환으로 처리하며 미지원 별칭을 무조건 통과시키지 않는다.
- **결과:** 현재 코드와 테스트에 최종 문자열 계약이 반영됐다.
- **한계:** 단위가 오간 실제 회의 이유, 이 변경으로 해결된 운영 오류의 건수·원 로그는 미확인이다. Ai 서버의 `unit` 쿼리 누락 사건과 동일 사건으로 합치지 않는다.

### D11. 제어 요청의 중복·만료·충돌을 가상 상태에 적용하지 않도록 했다

- **문제/제약:** 같은 명령의 재시도, 지난 명령의 늦은 도착, 반대 방향 장치의 동시 ON이 가상 상태를 잘못 바꿀 수 있다.
- **근거:** 8월 8일 가상 제어 도입, `VirtualActuatorService`, `ActuatorCache`, 8월 25일 로그 보강 및 테스트.
- **선택:** commandId와 요청 내용·시각·현재 상태를 함께 검사한다.
- **조치:** 초기 동기화 확인 → 기존 명령 재사용 확인 → 만료 → stale → 반대 장치 충돌 → 적용 순으로 처리한다. 정확히 같은 명령은 기존 응답을 돌려주고, 같은 ID의 다른 요청은 거부한다. 적용·거절·재처리 로그를 구분한다.
- **결과:** 명령 적용·정확한 replay·만료·stale·충돌·초기화 전 요청을 구분하는 코드와 테스트가 있다. 적용된 가상 상태는 다음 환경 갱신의 효과량에 반영된다.
- **한계:** `synchronized`와 command 이력은 프로세스 내부 범위다. 재시작 뒤 영구 멱등성을 보장하지 않는다. 현재 캐시에서 명령 이력의 시간 기반 자동 만료는 확인되지 않아 장기 실행 시 수명·크기 정책 검토가 필요하다. 실제 OOM이 발생했다는 뜻은 아니다.

### D12. 공유 상태를 삭제할 때 남은 센서까지 초기화되지 않게 했다

- **문제/제약:** 같은 EUI의 화씨만 삭제했다고 섭씨 관측값까지 지우거나, 한 장치를 삭제했다고 다른 장치가 쓰는 공용 환경을 지우면 잘못된 초기화가 된다.
- **근거:** `SharedGenerationStateLifecycle`, `SensorInfoEventService`의 삭제 순서와 관련 테스트.
- **선택:** 캐시에서 채널을 먼저 제거한 후 남은 참조를 확인한다.
- **조치:** 같은 EUI의 다른 단위 채널이 남으면 관측 상태 유지, 다른 EUI만 남으면 해당 장치 관측 상태만 제거, 마지막 참조가 없어질 때 공용 환경도 제거한다.
- **결과:** 단위 별칭 삭제·장치 삭제·마지막 채널 삭제를 구분하는 코드와 테스트가 있다.
- **한계:** 모든 상태 변경 경로의 원자성이나 장시간 스트레스 검증을 완료했다는 근거는 없다.

### D13. 구현이 바뀌었는데 저장소 루트 README에는 이전 구조가 남았다

- **문제/제약:** 문서의 독립 채널 Random Walk 설명과 현재 공용 환경 모델이 다르다.
- **근거:** 이번 조사에서 저장소 루트 README의 센서 채널 설명과 `SharedEnvironmentSensorValueGenerator`를 대조했다.
- **선택/조치:** 경험 문서에서는 현재 코드 기준으로 설명하고, 원 README는 작업 범위 밖이므로 수정하지 않았다.
- **결과:** 현재/과거 설계를 혼용하지 않는 기록을 남겼다.
- **한계:** 이것은 9월 14일 문서화 중 발견한 이슈이지 당시 개발 중 해결한 장애로 꾸며 쓸 수 없다. README 정리는 후속 작업이다.

## 6. 검증을 어떻게 설명할 것인가

이번에는 테스트를 실행하지 않았다. 아래는 **현 테스트 코드의 검증 의도와 기존 로컬 Surefire 기록**이다.

| 검증 축 | 코드에서 확인한 사례 | 채용 자료에서 말할 수 있는 범위 |
|---|---|---|
| 값 생성의 일관성 | 동일 cycle 재사용, stale 거부, 키별 독립, 동시 갱신 | “주기·키·동시 호출의 경계 조건을 테스트했다.” |
| 관측·단위 | 공용값→관측 투영→등록단위 변환, 미지원 변환 거부 | “센서 채널과 내부 표준 단위를 구분해 검증했다.” |
| 작업 예약 | 같은 재배 중복 차단, 거절·실패 후 해제 | “재배 단위 중복 실행과 예약 누수를 방지하는 경로를 테스트했다.” |
| 변경 이벤트 | 1개 이상 upsert, 빈 목록 종료, 중복키 부분 반영 방지 | “이벤트 계약의 모호한 목록 크기 분기를 제거했다.” |
| 가상 제어 | replay·충돌·만료·stale·초기화 전 요청 | “재시도 가능한 가상 제어 API의 상태 전이를 검증했다.” |

기존 보고서에 실패·오류 0인 일부 suite가 있지만, 보고서 생성 당시 SHA와 동일 실행 묶음을 확정하지 못했다. 합산 테스트 수나 최신 전체 통과 수를 성과로 적지 않는다. 대규모 성능 테스트·장기 안정성·현재 배포 완료는 별도 증거가 필요하다.

## 7. 향후 포트폴리오·자소서로 재사용하기

### 이력서 한 줄 후보

> Java/Spring 기반 가상 센서·액추에이터 서비스를 개발하고, 공용 환경과 장치 관측값 분리·단위 변환·MQTT 발행·재배 단위 실행 제어를 구현했습니다.

### 기술 사례 제목 후보

- 같은 환경을 다른 센서가 관측하도록: 독립 난수에서 공용 환경 모델로 전환
- 센서 개수가 시간의 속도를 바꾸지 않도록: cycleId 기반 상태 갱신
- 목록 크기를 업무 의미로 해석하지 않기: 임계값 이벤트 계약 수정
- `℃`와 `°C`의 차이: 단위도 API 계약으로 관리한 경험

### 경험 문장 초안 — 실제 이해·검토 범위에 맞게 수정

> 센서 시뮬레이터를 구현하면서 같은 재배의 센서들이 서로 무관하게 변하고, 단위가 다른 채널을 일관되게 연결하기 어렵다는 설계 한계를 확인했습니다. 재배별 공용 환경값과 장치별 관측 편차를 분리하고, 같은 생성 주기에는 상태를 재사용하도록 cycleId를 전달했습니다. 단위 변환, 동시 호출, 삭제 후 남은 참조, 작업 거절 후 예약 해제 사례를 테스트로 정리했습니다. 이를 통해 단순히 값이 생성되는 것보다 여러 서비스가 해석할 수 있는 일관된 데이터 계약이 중요하다는 점을 배웠습니다.

실제 문제 발견 장면·본인이 대안을 비교한 이유·팀원과 합의한 내용은 추가 확인 후 보강한다. AI 도구의 도움을 받은 코드를 모두 단독 수작업으로 작성했다고 표현하지 않고, 본인이 이해·판단·검토·검증한 범위를 설명한다.

## 8. 회고와 아직 남은 일

- **배운 점:** 시뮬레이터도 상태·동시성·단위·이벤트 계약을 갖는 서비스다. 센서값 생성 식 하나만으로 끝나지 않는다.
- **잘한 선택:** 공용 환경과 관측값 분리, cycleId 재사용, 제한된 executor, snapshot 준비 전 발행 금지, 명령 결과 재사용.
- **미완료/검토 필요:** README 현행화, 이벤트 revision/순서, readiness 통합, MQTT 유실 정책, 명령 이력의 수명, 다중 replica 전략, 실측 데이터 기반 보정.
- **추가 수집할 자료:** 변경 전후 같은 재배의 그래프, 섭씨·화씨 동시 관측 예, 실제 제어 요청·응답과 다음 값 변화, 정확한 배포 SHA, 통합 테스트 로그, 사건 당시 팀 논의 기록.
- **최신성 주의:** 로컬 저장소에는 8월 31일 이후 actuator 이벤트 마이그레이션 변경이 확인되지 않았다. 다른 서비스의 최신 변경을 이 저장소의 구현 완료로 옮겨 적지 않는다.
